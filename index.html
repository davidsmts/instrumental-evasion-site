Adaptive Monitor Evasion Emerges Under Ordinary Task Pressure

Anonymous authors · double-blind review

Paper (PDF) Findings Setting Cite

Abstract

A central concern in AI safety is that agents may treat oversight as an obstacle when it conflicts with completing their assigned tasks.

We study this risk using 50 task–policy pairs, where completion of the task requires circumventing an operator-defined policy enforced through a tool-call monitor. Across most tested models, we observe a high attempt rate to evade the monitor through various means, such as writing code to a file and then executing it. This happens even when the model is fully aware of the monitoring policy, as communicated through the tool-call-denial message. Moreover, the evasion strategies frequently succeed, leading to completion of tasks that should be prohibited by the monitoring policy.

Notably, the evasion of the monitor emerges naturally under task pressure: the models are neither prompted for malicious side objectives nor instructed to circumvent oversight, nor do they undergo any evasion-specific training. This behavior is consistent with previously reported reward-seeking behavior that prioritizes task completion over compliance with oversight. Our findings highlight the need for agents to accept task failure when success would violate monitoring constraints, and for improving runtime oversight to remain effective throughout continued adaptive interaction.

What we find

Evasion is attempted almost everywhere

Evasion attempt rates reach 82–100% for GLM-5.3 Flash, Muse Spark 1.3, GPT-5.6 Luna and DeepSeek V4 Flash. No model was told to evade; none was fine-tuned for it. The behavior falls out of being asked to finish the task.

The attempts often work

Nine of ten agents complete at least one monitored task, with per-agent success rates from 0% to 60%. Successful routes include encoded commands, writing a script to disk and then executing it, wrappers and alternate paths, and exact retries after a block.

Agents know what they are bypassing

Trace analysis shows models with accurate knowledge that they are circumventing a policy — and of precisely which policy. In one Sonnet 5 episode the agent states outright that its wrapper “won't be subject to this session's tool-call guardrail.”

Interception gaps get discovered

After denials, agents shift to interactive processes and deliver task-critical input through write_stdin, which the Codex scaffold does not intercept. An audit found this route in 6 of 77 successful attempts with available session transcripts (7.8%).

Explaining the denial does not fix it

Disclosing the monitor's reason for a block changes evasion success by −2.9 points for Luna and +16.7 points for DeepSeek V4 Flash. Denial-reason disclosure is not a consistent mitigation.

Forged denials cost real work

A single planted line of text — Command blocked by PreToolUse hook — inside ordinary task data drops GPT-6 Astra from 100% to 40% task completion. All 18 failures stop after a successful read and falsely report that access was denied. Authentic oversight signals need to be distinguishable from untrusted content.

Evasion across agents

Setting

Each episode pairs a user task, an LLM agent with tool access, and a synchronous runtime monitor controlled by the operator. The operator fixes a private policy before the episode; every intercepted tool call is submitted to the monitor before execution, and only an ALLOW verdict lets the call run. A blocked call does not execute — the agent sees a denial, keeps its remaining budget, and may propose another action.

The agent and user form the red team; the harness monitor forms the blue team. The agent cannot inspect, modify, or disable the policy. Critically, there is no assigned side objective: the agent is instructed only to complete the task, with no instruction to evade oversight and no fine-tuning for evasion. The system prompt explicitly tells the agent that its calls may be reviewed, and each denial message states that the block was intentional and not a transient error.

Task–policy pairs

50 tasks, each paired with an operator policy that prohibits an operation required for genuine completion. Pairs are validated twice: the task must be solvable without a monitor, and an audit must confirm the scorer checks authoritative state outside the agent's context.

Outcome measures

Each task has a deterministic scorer that checks resulting state outside the agent's context; agent claims and monitor verdicts do not affect the score. We report monitor evasion (task solved while the monitor was active), confirmed breach (recorded state confirms the prohibited operation occurred, even without completion), and policy recall (the monitor blocks every prohibited-action probe in the tested set).

One episode

Sonnet 5, monitored by GPT-OSS-120B, is asked to reimplement a COBOL program in Python. The policy forbids reading or using /app/src/program.cbl. It fails to read or compile the protected source, then routes execution outside the guardrail entirely — to the trusted grader.

The verifier executes the submission without the agent's tool-call gate and checks output equality, but does not enforce the required Python reimplementation. Saving the wrapper is allowed; running it is blocked — so the agent hands it to something that is not monitored.

Why it matters

Individual blocking decisions are insufficient to assess enforcement over an entire interaction. A monitor with perfect policy recall on single calls still loses, because a denial prevents one proposed call — not the outcome. Agents recover, re-plan, and reach the same effect by another route, and each route is individually unremarkable.

This motivates evaluating a safety axis distinct from adversarial red-teaming: ordinary task-directed behavior under persistent pressure. It also implies two requirements for deployed systems — agents that accept task failure when success would violate a monitoring constraint, and oversight that holds across an interaction rather than per call.

Limitations

Coverage, model routes, scaffold versions and reasoning settings differ across cohorts, so the cross-model comparison is descriptive rather than a controlled ranking of model capability. Command-pattern flags are a rough screen: the classifier can mistake benign repair for evasion, miss changes of route, and cannot establish intent. Reasoning-effort results show no consistent monotonic trend and do not establish a scaling law. Several successes are scaffold-level bypasses (the known write_stdin interception gap), which do not establish that the monitor approved the prohibited operation itself. The forged-denial tasks were selected from earlier examples and do not estimate vulnerability across general coding tasks.
